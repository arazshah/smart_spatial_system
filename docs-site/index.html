Ask a geospatial question in plain language.
Get a reproducible answer back.

Smart Spatial System is a plugin-based GeoAI backend. A question like "rank these candidate sites by distance to metro, schools and parks" becomes a structured plan, executes through vector, raster and PostGIS plugins, and returns map layers, tables and reports — with a full execution trace, and a deterministic path alongside the LLM one so "is this reliable" is a measured number, not a guess.

Why this, not a general LLM agent with GIS tools

Reliability you can measure, not assume

The obvious alternative is handing an LLM function-calling access to some GIS functions. This project deliberately doesn't stop there — for reasons that turned out to matter in practice, not just in theory.

A deterministic path, from the same catalog

The same analysis can run by rule or by LLM, built from one shared OP_CATALOG. That makes "is the LLM's plan reliable?" a measurable question — Plan Agreement Rate, Rank Stability — not a leap of faith.

Every plan is validated before it runs

Missing input roles, unchained multi-factor scoring, asymmetric CRS reprojection, an untyped scoring factor — each is a distinct, previously-silent failure this system now catches and names before spending a second executing.

Every run carries a full trace

Which operations ran, in what order, with what parameters. A wrong answer is debuggable, not a black box you have to trust.

Not a design argument — evidence

  • Five correctness bugs found and fixed via the Vienna reproducibility case study, documented in the CHANGELOG (0.2.1–0.2.4): a silent domain-wrong default, an undocumented required input role, un-chained multi-factor scoring, an asymmetric CRS mismatch, and a scoring factor silently defaulting to the wrong type.
  • Three more found and fixed via the Tehran TOD-gradient case study (0.2.5–0.2.9), running a real LLM (gpt-4o-mini) against real OpenStreetMap data: a missing multi-ring buffer primitive, a boolean-filter-vs-zone-preserving-join planning choice, and a spatial_join cardinality default that silently dropped matches.
  • Nine more found and fixed through the İstanbul health-access case study (0.4.1–0.5.6): 6 bug reports and 3 enhancements. The fixes include the shape of the where value, explicit None overriding defaults, a CRS leaked from a prompt example, a projected CRS derived from the data, and a repair retry. At 0.5.6, 20/20 unhinted LLM-planned runs match the answer written by hand exactly.
  • Each was root-caused from source, fixed at both the plugin layer (protects every caller) and the LLM-prompt/validation layer (catches what the prompt can't guarantee), and shipped with regression tests reproducing the exact failure.
  • See smart-spatial-vienna-accessibility and smart-spatial-tehran-tod-gradient and examples/istanbul_health_access for the case studies that found them.

Research

Built to be studied, not just used

The full catalog — including what isn't a good fit yet — is in docs/CASE_STUDIES.md. Four studies written with s3geo so far: Vienna, Tehran, İstanbul (complete, with a full paper) and Urmia. Six more are proposed below, plus the reference pattern they all build on.

The reference pattern: reproducibility of LLM vs. rule-based plans

smart-spatial-vienna-accessibility — Vienna district accessibility to metro, schools and parks — runs the same analysis two ways from one operation catalog, and measures whether the LLM path agrees with itself and with the deterministic one.

Any study below can reuse this exact methodology as its evaluation section.

Done and in progress

Three follow-on studies building on this

HEALTH

İstanbul health access

Which of 964 İstanbul mahalle are underserved by 1,020 hospitals and clinics? This study is complete: paper, notebooks and figures are in the repo. At 0.5.6, 20/20 LLM-planned runs match the rule-based answer exactly (Jaccard 1.0). The CRS in those runs was derived from the data. The study drove fixes in 0.4.1–0.5.6.

TOD

Tehran metro TOD gradient

Land-use diversity vs. distance from 122 Tehran metro stations, real OSM data. Manual arm done; the LLM arm surfaced and fixed three more defects (0.2.5–0.2.9), and its output is now bit-identical to the hand-authored pipeline.

RE

Urmia real-estate ranking

Real-estate suitability ranking against real Urmia OSM data (transit/mall/road proximity, flood/earthquake/fire risk, allowed-construction zoning), reusing this system's shipped real-estate workflow end to end. Scaffolded, not yet run.

Get started

Two ways in — library or HTTP

Both first-class. Complete runnable versions of both are in examples/ in the repository.

from orchestrator.capability_registry import CapabilityRegistry
from orchestrator.planning.dag_executor import DagExecutor
from orchestrator.planning.planner import DeterministicPlanner
from smart_spatial_system.application.services.query_execution.accessibility_query_spec import (
    AmenitySpec, build_accessibility_initial_inputs, build_accessibility_query_spec,
)

amenities = [
    AmenitySpec(ref="metro", distance_field="distance_to_metro_m",
                max_distance_m=800.0, weight=3.0),
    AmenitySpec(ref="schools", distance_field="distance_to_school_m",
                max_distance_m=1200.0, weight=2.0),
]

query_spec = build_accessibility_query_spec(
    "Rank sites by access to metro and schools", amenities,
    target_crs="EPSG:31256",  # a projected CRS - degrees ≠ metres
)

plan = DeterministicPlanner().build(query_spec)
registry = CapabilityRegistry.from_plugin_modules(tolerant=True)
result = DagExecutor(lambda name: registry.resolve(name).callable).execute(
    plan,
    initial_inputs=build_accessibility_initial_inputs(
        sites=sites_geojson,
        amenity_layers={"metro": metro_geojson, "schools": schools_geojson},
    ),
)

s3geo.query() wires up OpenAICompatibleLLMClient + LLMQuerySpecGenerator
+ DeterministicPlanner + CapabilityRegistry + DagExecutor - the exact
pipeline the "As a library" tab builds by hand - for when a question
just needs answering. `layers` accepts GeoJSON FeatureCollections or
GeoDataFrames interchangeably. Needs a real LLM key (LLM_API_KEY /
AVALAI_API_KEY / OPENAI_API_KEY). New in v0.3.0.

v0.4.0: every one of those classes - plus s3geo.registry() and the
errors query() can raise - is re-exported as s3geo.<Name>, the exact
same object orchestrator.* defines, not a copy. import s3geo is enough
on its own, for the one-call path or full manual control either way.
import json, urllib.request

body = {"query": "Display the sites on the map", "inputs": {"vector": sites_geojson}}
req = urllib.request.Request("http://127.0.0.1:8000/query",
                             data=json.dumps(body).encode(), method="POST")
req.add_header("Content-Type", "application/json")
req.add_header("X-API-Key", "...")  # when the server requires a key
response = json.loads(urllib.request.urlopen(req).read())

for layer in response["layers"]:
    print(layer["name"], layer["summary"]["feature_count"])
