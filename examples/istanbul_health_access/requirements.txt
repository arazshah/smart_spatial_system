# BUMPED 0.3.0 -> 0.4.1 -> 0.4.2 -> 0.5.0 (2026-09-19): closes bugs/002

# 0.5.0 is a performance fix, not a correctness bug, so it has no
# matching bugs/ report here - reported directly upstream instead:
# plugins/nearest_neighbor.py::find_nearest_neighbors computed nearest
# neighbors with a brute-force O(source * target) nested loop (no
# spatial index anywhere in the file - grepped and confirmed before
# reporting it), which is very likely why this repo's s3geo.query()
# calls were taking ~120-130s each on the 964 mahalle x 1020 hospital
# dataset. Fixed by adding an STRtree-accelerated candidate search
# (shapely-only; engine="python" and any shapely-unavailable/geometry-
# parse-failure case still use the original nested loop unchanged, so
# nothing here is silently approximated). CHANGELOG.md [0.5.0] reports
# ~33s -> ~0.2s (~150x) on a synthetic 1000x1000 benchmark and ~32s ->
# ~0.2s on this repo's own 964x1020 shape specifically, with identical
# output - confirmed by cloning github.com/arazshah/smart_spatial_system
# at tag v0.5.0 and reading the actual diff in plugins/nearest_neighbor.py
# (STRtree import, _strtree_candidates(), spatial_index_used metadata
# field) and tests/test_nearest_neighbor_strtree_performance.py (both a
# correctness-equivalence test against the old brute-force path and a
# performance benchmark) directly - not taken on the upstream fixer's
# word alone. `bugs/002`/`bugs/003`'s local mitigations are still moot
# as before; bugs/004 (where-clause shape) is unaffected by this bump,
# still open.

# BUMPED 0.5.1 -> 0.5.2 (2026-09-23): closes bugs/006 (filter_attribute's/
# sort_limit's sort_order rejected an explicit null instead of falling
# back to its own "asc" default - an LLM plan that includes
# "sort_order": null, the same "every advertised key gets a value, null
# for the ones not used" pattern bugs/004 already documented, overrode
# the Python default instead of triggering it, and unlike the sibling
# param bbox_mode - which already tolerated None via pick_first() - this
# one didn't). Fixed twice over, per CHANGELOG.md [0.5.2]: (1)

# pick_first(sort_order, default="asc"), matching bbox_mode exactly; (2)
# DagExecutor._build_kwargs now drops any None-valued static param whose

# doesn't accept None (new _drop_none_overriding_defaults()/
# _annotation_allows_none() helpers, wired in via the resolved
# capability_fn) - a systematic fix at the executor level, catching the

# unmatched/template_name used to raise the same way; descending,
# drop_outside, skip_missing, save_to_disk, and several field-name params

# non-None-default None, which would have silently rewritten
# calculate_attribute_statistics(precision=None) - where None legitimately
# means "don't round" - to the default 6; fixed by only dropping None when
# the parameter's own annotation doesn't declare it acceptable. New
# tests/test_op_catalog_none_param_defaults.py covers the sort_order
# regression, end-to-end filter_attribute/sort_limit runs, and a
# catalog-wide check. Confirmed for real by cloning
# github.com/arazshah/smart_spatial_system at tag v0.5.2 and reading both
# commits' actual diffs directly, plus executing the plugin-level fix in
# this session (filter_features(sort_order=None) now returns cleanly

# BUMPED 0.5.2 -> 0.5.3 (2026-09-23): closes bugs/004 (filter_attribute's
# `where` and enrich_feature_properties's `rules` are structured params
# whose value SHAPE was never taught to the LLM - only the key name was,
# via _op_param_reference() - so a capable model guessed a SQL-style
# string for `where` and produced `rules` entries missing the required
# `target` key, both fully documented in their own plugin's docstring and
# neither reaching the prompt). Fixed two ways, per CHANGELOG.md [0.5.3]:
# (1) new orchestrator/planning/op_param_shapes.py - a maintained
# PARAM_SHAPES table, keyed by (capability_name, target_kwarg), with a
# description and real JSON examples for every structured OP_CATALOG
# param (not just where/rules - also score_features.factors,
# enrich_risk's params, join_feature_properties.fields, the raster
# params, etc.), rendered into the system prompt as a new "Structured
# param VALUES" section right after the existing key-list section; a new
# test (tests/test_op_param_shapes.py) fails if any structured param_map
# target lacks an entry, and - importantly - runs every example through
# the REAL plugins, so a wrong example fails the suite instead of
# teaching the model a wrong shape; (2) a new generation-time validator,
# _validate_structured_param_shapes(), rejects a mis-shaped where/rules
# with a clear LLMSpecGenerationError (naming the op, its output ref, and
# a correct example) instead of letting it fail at execution after a full
# DAG build - its operator set is asserted equal to
# spatial_query_filter.py's own VALID_OPERATORS by a dedicated test, so
# the two can't silently drift apart. Upstream is explicit that this was
# NOT spot-checked against a live LLM (no endpoint/API key available when
# 0.5.3 was cut) - the tests confirm the guidance is present and its
# examples are accepted by the real plugins, not how often a model now
# produces a valid value; this repo's next N=20 batch is the real
# measure. Confirmed for real in this session: cloned
# github.com/arazshah/smart_spatial_system at tag v0.5.3, read the actual
# diff (orchestrator/planning/op_param_shapes.py,

# claims. All three bugs found in this study's Phase 4 work (bugs/004,
